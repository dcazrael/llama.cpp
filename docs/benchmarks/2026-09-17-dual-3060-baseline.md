## Confirmed transport behavior

With `NCCL_P2P_DISABLE=1`, NCCL selected `SHM/direct`.

With `NCCL_P2P_LEVEL=PHB`, NCCL reported `isAllDirectP2p 1` and selected `P2P/direct pointer` in both directions.

Therefore direct GPU-to-GPU P2P is genuinely working on this machine.

## Major problem discovered: GPU1 thermal throttling

The matrix is not a clean performance comparison because GPU1 heated progressively during sequential runs.

Representative active-load telemetry:

- Run 01 layer: GPU1 average 73 C, max 83 C, average SM clock ~1867 MHz.
- Run 02 layer: GPU1 average 86.8 C, max 91 C, average SM clock ~1675 MHz.
- Run 03 tensor: GPU1 average 92.5 C, max 93 C, average SM clock ~1359 MHz.
- Run 04 tensor: GPU1 average 92.6 C, max 94 C, average SM clock ~1234 MHz.
- Run 05 tensor P2P: GPU1 average 92.7 C, max 94 C, average SM clock ~1229 MHz, minimum ~892 MHz.
- Later runs remained around 92-94 C and mostly ~1.2-1.3 GHz on GPU1.

GPU0 generally remained around 1.9 GHz under load.

This thermal asymmetry is large enough to distort:

- device-order comparisons,
- P2P vs SHM comparisons,
- tensor-split ratio comparisons,
- comparisons against earlier cold-start results.

Do not use this matrix to choose a final transport or split ratio.

## What is still useful from this matrix

1. Direct P2P is functional.
2. Tensor mode materially improves decode relative to layer mode even under the thermal disadvantage. Best tensor TG in this matrix was 28.55 t/s vs 18.92 t/s for the best layer run, roughly +51%.
3. Layer mode currently gives stronger PP in this thermally-confounded run: 772.97 t/s vs 722.60 t/s for the best tensor result in this matrix.
4. Device ordering and tensor split clearly affect performance, but the effect cannot yet be separated from GPU1 thermal throttling.
5. The earlier cold P2P run on build `73a43d1f6` measured 795.82 pp4096 and 30.02 tg128 using CUDA1/CUDA0 and 6/5, which is substantially faster than the later hot run. This strongly motivates a controlled cold/cooldown retest before attributing the difference to llama.cpp commits.

## Upstream-version note

The earlier build `73a43d1f6` is an upstream llama.cpp commit. The new branch parent `83078fec0` is 176 upstream commits newer. There are many CUDA changes between them, including all-reduce and CUDA backend changes, so a commit-level performance regression remains possible. However, thermal state must be controlled before testing that hypothesis.

## Required next step

Do not start source optimization yet.

First make the benchmark thermally controlled:

1. Investigate GPU1 cooling / thermal throttling.
2. Record fan speed and clocks-event/throttle reasons.
3. Start every A/B pair from a comparable GPU temperature, or insert a cooldown gate between runs.
4. Interleave or randomize paired tests rather than running all variants sequentially.
5. Re-run a small matrix first:
   - layer 6/5
   - tensor 6/5 SHM
   - tensor 6/5 P2P
   - same preferred device order
6. Then repeat the old `73a43d1f6` P2P test under the same thermal conditions to determine whether the 176-commit difference itself changed performance.

Only after this controlled rerun should we choose the generic dual-GPU optimization baseline.
