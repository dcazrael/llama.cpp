# 2026-09-17 Fast Path Decision

Goal: stop expanding the benchmark/setup loop and get a usable dual-GPU daily driver quickly.

## Decision

Use the existing cold benchmark as the working performance baseline for Qwen3.8 27B:

- build: upstream commit `73a43d1f69345aee8bb186ef4b3172cef892f2e5`
- model: SuperQwen3.8-27B Q4_K_M
- devices: `CUDA1/CUDA0`
- split mode: tensor
- tensor split: `6/5`
- NCCL P2P forced across PHB
- pp4096: `795.82 t/s`
- tg128: `30.02 t/s`

The later 12-run matrix is retained as diagnostic data, but it is not the performance baseline because GPU1 was thermally saturated before most tensor tests.

## Branch state

`dual-gpu-opt` currently contains documentation only. No llama.cpp source optimization has been applied yet.

Do not spend more time trying to perfect the benchmark matrix before producing a usable runtime.

## Fast path

1. Keep `master` as upstream mirror.
2. Keep `dual-gpu-opt` as the integration branch.
3. Pin the current integration base instead of continuously rebasing while optimizing.
4. Establish a working Qwen3.8 27B server preset first using the already proven tensor/P2P settings.
5. Use that as the daily-driver/control workload.
6. After the daily driver is operational, begin Flash-Next-specific work.
7. First Flash-Next source optimization: QSA indexer token chunking, because it directly targets the long-context scratch/workspace problem while preserving the generic dual-GPU base.
8. Next evaluate QSA decode paths (gather vs sparse FA), then pooled-key cache, then expert cache.
9. Generic dual-GPU improvements are added only when there is a concrete measured bottleneck; do not block Flash-Next progress on exhaustive multi-GPU research.

## Practical rule

From this point, optimization work should answer one of two questions:

- Does it make the dual-3060 daily driver faster/more stable?
- Does it remove a specific Flash-Next bottleneck?

If not, defer it.
